Requirements for the Agentic-Enabled SOC Persona

WG3 — Agentic-Enabled SOC Reference Architecture· architecture dated 2026-08-06· this spec 2026-09-15· owner: ONUG Collaborative
WG3 kept WG2's skeleton on purpose — same four boxes, same six-step loop, "per the shared-template agreement." What changes is exactly what a security operations center needs changed: a conservative autonomy ceiling, a Decide Gate instead of a Verify Gate, and an audit journal that has to double as chain of custody.

Scope and method

Like WG2, WG3 has no separate numbered requirements list. The WG2/WG3 v0.6 NOC/SOC reference architecture is the drawing this document numbers, element by element. Where the drawing's step names conflict with the older AI SOC Reference Architecture technical reference, both are cited and the conflict is flagged rather than silently resolved — see the note under Agent Operations Loop.

This is the SOC application of the same skeleton WG2 uses for the NOC. Requirements that are identical in structure to WG2's are stated in SOC-specific language below; see the WG2 requirements document for the network-operations version.

Lineage — tracing back to the 25

Every requirement below now cites the WG1 item it descends from, matching WG1's and WG2's requirements documents so all three trace to one list.

  • WG1's Agentic Overlay Alignment Analysis is the only numbered requirements source across the WG1–3 set. WG3's v0.6 drawing has no numbers of its own — the citations below are this document's analysis, not a working-group-ratified crosswalk.
  • The v0.6 reference architecture already names three of these connections (persona → item #18, next-hop auth → item #21, composite authority → item #22); the rest are extended here to cover every requirement.
  • Two SOC-specific items get pulled in that WG2 doesn't need: item #19, Agent Inferred Prompt Injection — relevant wherever an LLM-based agent parses attacker-influenced log or alert content — and the same item #20, Credential-in-Context Protection, at the Respond step.

How to read the drawing

Quoted directly from the architecture map's own labels.

Agent Persona Creation Access Enforcement & Audit Agent Operations Loop 1–6
  • Same plan-then-build structure as WG2. Persona creation (autonomy, model, estate) must be answered before enforcement and the loop can be built.
  • The SOC ceiling is conservative by design. Where WG2's L3 is earned by track record generally, WG3's L3 is scoped narrowly — "corroborated known-bad signatures only."
  • Green = read-only, orange = autonomy-gated — same color coding as WG2. Steps 1–3 always run; steps 4–6 are gated by the persona's autonomy level.

PER-1item #1
rel. #6
Agent Autonomy Level

Four levels, with a SOC-specific ceiling: L0 observe, L1 recommend, L2 gated act ("analyst approves each block"), L3 bounded auto-act ("corroborated known-bad signatures only"). This level decides whether loop steps 4–6 ever fire.

This is WG1 item #1's risk-tier and decision-rights model, scoped conservatively for a SOC persona. Related: item #6, Human Oversight Policy. The older AI SOC Reference Architecture technical-reference doc defines a differently-scoped three-level framework (Level 1 Inform/Suggest, Level 2 Bounded Auto-Containment, Level 3 Full Machine Autonomy). The two schemes are not reconciled in the source material — treat the v0.6 drawing's L0–L3 as current.
PER-2item #10
Models & Model Location

On-prem versus frontier is a risk decision: design for retries on off-premises calls, account for public-pretraining contamination. SOC-specific: ML handles anomaly scoring, NLP/LLM handles log semantics. No GPU fabric is required — the build standard matters, not the cluster.

Maps to WG1 item #10's model-security requirements, applied to detection models rather than action-taking ones.

rel. #18
Estate Under Watch

Endpoints/EDR, identity systems, cloud IAM & flows, internet edge/CDN/WAF — with fused detection across all of them, not siloed per source.

The "connected systems / data accessed" field from WG1 item #4's Inventory and Registry, scoped to the SOC persona. Related: item #18, Agent Personas.

Agents / MCPs

Governed, reachable only under explicit control of which agents may talk to which. For the SOC this is what makes fused detection possible — endpoint, identity, cloud, and edge agents correlating under control — including SOC⇔NOC coordination, such as quarantining a host without tipping off the intruder.

Item #16, Multi-Vendor Control Plane Interoperability, applied across internal domains rather than external vendors. Related: item #21 (per-hop auth) and item #22 (the aggregate risk of many correlating agents).

Agent Operations Loop 1–6

"the autonomy level chosen above decides whether steps 4–6 ever fire" · "intelligence value may outweigh immediate blocking"

The v0.6 drawing names these steps Detect · Investigate · Propose · Decide · Respond · Validate & Learn. The older technical-reference doc names the same six positions Detect · Diagnose · Propose · Verify Gate · Execute · Validate, with per-step authority-scope detail this drawing doesn't spell out. The content lines up 1:1; the names don't match and the source material never reconciles them. Both are given below.

LOOP-1item #8
rel. #19
Detect

Signal surfaces. Read-only.

Per the older reference doc: "read-only / high-throughput ingestion" across EDR, cloud, identity, NDR, and AI-API telemetry — the ingestion half of item #8. Related: item #19, since this is where adversary-influenced log content first reaches an agent.
LOOP-2item #8
rel. #9
Investigate (called "Diagnose" in the older reference)

Context and scope. Read-only.

Per the older doc: "read-only graph queries and source-of-truth lookups" across the Unified Security Graph, without manual pivoting between tools — item #8's investigation half, drawing on item #9's audit data.
LOOP-3item #6
rel. #1
Propose

Candidate action. Read-only — an analyst still decides; nothing here is mutable.

Per the older doc: "read-only proposal generation and impact assessment," not execution of a fixed static playbook — item #6's Human Oversight Policy in practice. Related: item #1's decision-rights matrix.
LOOP-4item #7
rel. #6
Decide — Decide Gate (called "Verify Gate" in the older reference)

Weighs contain-now versus observe-and-trace. Read-only — nothing changes yet.

Per the older doc: a "Mother-May-I" change-stop check with dry-run and required rollback plan; low-risk actions pass automatically, high-impact actions (e.g. taking a primary database offline) require human authorization. This is item #7's runtime guardrails (confidence thresholds) executing; item #6 covers the human-authorization branch.
LOOP-5item #5
rel. #20
Respond (called "Execute" in the older reference)

Staged, ticketed monitor → flag → block. Never blanket. This is the one genuinely mutable step in the loop.

Per the older doc: ephemeral, scoped service credentials at the control-plane/API layer; auto-files an ITSM/change ticket — item #5's IAM Standard. Related: item #20, since the credential is injected at this boundary and never held by the agent.
LOOP-6item #13
rel. #9
Validate & Learn

Confirm the response worked; feed the outcome back into learning rather than merely observing it.

Per the older doc: confirms neutralization (e.g. C2 traffic stopped, token disabled), auto-triggers rollback and escalates to L3 on failure or unintended degradation — item #13's Incident Response recovery process. Related: item #9 — the outcome becomes chain-of-custody evidence.

Out of scope / open questions

  • Hierarchical vs. full-mesh agent topology, cross-domain read-access authority, centralized vs. distributed audit, and where guardrails/AOMC live — the same four open questions WG2 carries forward; not SOC-specific, not resolved.
  • Loop step names are unreconciled between the v0.6 drawing and the older technical-reference doc — see the note under Agent Operations Loop above. Anyone citing a step name should specify which document.
  • "AOMC" is an acronym collision. In the AI SOC Reference Architecture technical reference it expands to "Autonomous Operations Management Console"; in the three sibling WG1 documents it means "Agentic Overlay Mandatory Controls." Same working-group ecosystem, same acronym, different referent, not reconciled anywhere in the source.
  • The tiered-autonomy naming conflict noted under PER-1 (L0–L3 vs. Level 1–3) is unresolved.
  • The older reference doc states a 45:1 non-human-identity ratio and "millions of events per day" without citation — treat as unverified working-group color, not a sourced figure.
  • Both v0.6 drawings are dated August 6, 2026, but the WG3 file cites WG3 sessions only through 7/23 while the WG2 file it borrows its skeleton from cites sessions through 7/28.
  • This is a v0.6 working draft prepared for vendor sessions — not a ratified reference architecture.
