Requirements for the Autonomous NOC Persona

WG2 — Autonomous Infrastructure Reference Architecture· architecture dated 2026-08-06· this spec 2026-09-15· owner: ONUG Collaborative
The drawing says plan, then build, and draws exactly two boxes: persona creation on top, enforcement and audit below. You can't do anything in the bottom box until the top box is answered. This document turns each labeled element of both boxes, plus the six-step loop between them, into a checklist.

Scope and method

WG2 has no separate numbered requirements list the way the WG1 scoping document (Agentic Overlay Alignment Analysis) gives WG1. What it has instead is the WG2/WG3 v0.6 NOC/SOC reference architecture — a v0.6 architecture drawing whose every box and invariant is already a requirement, just not numbered. This document numbers them, one requirement per labeled element, in the order the drawing places them: persona first, then enforcement, then the operational loop.

This is the NOC half of a shared skeleton. WG3's SOC architecture uses the identical four boxes and six-step loop "by explicit agreement" — see the companion WG3 requirements document for where the two diverge.

Lineage — tracing back to the 25

Every requirement below now cites the WG1 item it descends from, so all three working groups' requirements trace to one list.

  • WG1's Agentic Overlay Alignment Analysis is the only numbered requirements source in the WG1–3 document set. This drawing has no numbers of its own — the mapping below is this document's own analysis, matching what each box and step does to the WG1 item that already describes that capability. It has not been reviewed or ratified by the working group — treat it as a proposed crosswalk, not an agreed one.
  • A few of these connections were already named in the v0.6 reference architecture itself (persona → item #18, next-hop auth → item #21, composite authority → item #22); the rest are extended here to cover every requirement, not just those three.
  • Where a requirement clearly serves more than one WG1 item, the primary citation is the closest match and a related item is named alongside it.

How to read the drawing

Quoted directly from the architecture map's own labels.

Agent Persona Creation Access Enforcement & Audit Agent Operations Loop 1–6
  • Plan, then build. "You can't do anything below unless you know what you're going to allow up here." Persona creation is theoretical; enforcement is implementation. The autonomy level chosen in persona creation decides whether the loop's action steps ever fire.
  • Green = read-only, orange = autonomy-gated — the drawing's own color coding, kept below. Loop steps 1–3 are read-only and always run; steps 4–6 only fire if the persona's autonomy level allows it.
  • One generic template, pluggable per domain (network, server, WAN, SOC). WG2 built it for the NOC; WG3 applied the same skeleton to the SOC.

Agent Persona Creation

"you can't do anything below unless you know what you're going to allow up here"

Three decisions, made together — the 7/28 working session's reframing was that these aren't three separate choices, they are the agent's persona.

PER-1item #1
rel. #6
Agent Autonomy Level

Define four levels — L0 observe, L1 recommend, L2 gated act, L3 bounded auto-act. This level decides whether loop steps 4–6 ever fire. Assignment is risk-tolerance dependent and earned by track record, not granted up front.

This is WG1 item #1's risk-tier and decision-rights model, applied to one persona. Related: item #6, Human Oversight Policy — the override procedures an autonomy level ultimately answers to.
PER-2item #10
rel. #17
Models & Model Location

On-prem versus frontier is a risk decision, not a performance one: design for retries on off-premises calls that can fail mid-operation, and account for the contamination risk public pretraining carries that an on-premises model doesn't. Every model must be certified, version-pinned, and rolled back on regression.

Maps to WG1 item #10's model-security and resiliency requirements. Related: item #17, Private Open Routing — the on-prem/frontier choice is a sovereignty decision as much as a security one.
PER-3item #4
rel. #18
Estate Under Management

Define the scope this persona may see and touch — DC fabric, public cloud, WAN/branch — with a control gradient per domain. The definition must be pluggable to any domain, not NOC-specific.

This is the "connected systems / data accessed" field from WG1 item #4's Inventory and Registry, scoped to one persona. Related: item #18, Agent Personas.

Access Enforcement & Audit

"outside agent control and influence" · "enforcement means any access control — identity, certificates, zero trust — not just firewalls and ACLs"

Two valid access patterns and four governed resource classes. The drawing is explicit that vendors should be shown both patterns, not asked to pick one.

ACC-1item #21
Pattern A — Direct (agent ⇔ agent)

Support agents reaching resources and each other directly, where every agent-to-agent call carries the same enforcement as any other access. Proven at production scale, but described in the source as "hard-won" — not the easier path.

This is WG1 item #21, Agent-to-Next-Hop Authentication, in its most literal form: every direct agent-to-agent hop must carry cryptographic proof of identity.
ACC-2item #7
rel. #5
Pattern B — Orchestrated

Support an Orchestrator / AI Gateway that fronts all four governed resource classes. The orchestrator must sit inside enforcement and reference policy on every request — it is never a trusted superuser, regardless of how central its position looks.

The orchestrator's per-request policy check is WG1 item #7's technical/runtime guardrails, centralized at one gateway. Related: item #5, least-privilege access.
RES-1item #8
Telemetry / Logs

Governed resource, reachable only as policy allows, under either access pattern.

The raw feed WG1 item #8's Observability and Monitoring is built on.
RES-2item #8
rel. #9
Sources of Truth

Governed resource, reachable only as policy allows, under either access pattern.

The baseline data item #8's anomaly detection compares against. Related: item #9, Audit and Traceability.
RES-3item #7
Rulesets

Governed resource, reachable only as policy allows. An agent reads its own rules but can never modify them.

The ruleset is WG1 item #7's technical guardrails (allowed/restricted/denied) — read-only enforcement of it is what keeps it a guardrail and not a suggestion.
RES-4item #16
rel. #21, #22
Agents / MCPs

Other agents and MCP servers are themselves a governed resource, reachable only under explicit reachability control of which agents may talk to which. New in this draft, and the direct fix for "we've automated the silos" — a cloud symptom whose root cause is a NIC only gets correlated if agents can reach across domains, under control.

This is WG1 item #16, Multi-Vendor Control Plane Interoperability, applied within one enterprise's domains rather than across vendors. Related: item #21 (the per-hop authentication that makes reachability enforceable) and item #22 (the aggregate risk of many agents reaching many other agents).

Agent Operations Loop 1–6

"the autonomy level chosen above decides whether steps 4–6 ever fire" · "only one box in the whole loop can mutate state, and it's visually unmistakable"

Common to both access patterns. Steps 1–3 are read-only and always run; steps 4–6 are gated by PER-1's autonomy level.

LOOP-1item #8
Detect

Signal surfaces. Read-only.

The ingestion half of item #8, Observability and Monitoring.
LOOP-2item #8
rel. #9
Diagnose

Root cause and scope. Read-only.

The investigation half of item #8; draws on item #9's audit data to establish scope.
LOOP-3item #6
rel. #1
Propose

Candidate fix. Read-only — a human implements the change; nothing in steps 1–3 is mutable.

A proposal exists to be approved — this is item #6's Human Oversight Policy in its most basic form. Related: item #1's decision-rights matrix decides who approves it.
LOOP-4item #7
rel. #6
Verify — Verify Gate

Change-stop check, dry-run, blast-radius assessment, rollback plan. Read-only — nothing has changed yet at this step.

This gate is item #7's runtime guardrails (confidence thresholds, scope boundaries) executing. Related: item #6 — high-impact changes route to a human here.
LOOP-5item #5
rel. #20
Execute

The mediated, ticketed write. This is the one genuinely mutable step in the entire loop.

Ephemeral, scoped service credentials at this step are item #5's Agent IAM Standard in action. Related: item #20 — the credential is injected at this boundary, never held by the agent itself. Every other requirement in this document exists to constrain what happens here.
LOOP-6item #13
rel. #9
Validate

Confirm outcome.

Auto-rollback and escalation on failure is item #13's Incident Response recovery process, running automatically. Related: item #9 — the outcome becomes part of the audit record.

Boundary constraints

Stated in the drawing as invariants that hold across every persona, pattern, and loop step above — not a separate requirement, but the rule each one above is built to satisfy.

Out of scope / open questions

Carried forward from the drawing itself — the working group named these as unresolved, not as gaps in this document.

  • Hierarchical vs. full-mesh agent topology — undecided.
  • Who holds cross-domain read-access authority — undecided.
  • Centralized vs. distributed audit — undecided.
  • Whether guardrails/AOMC run as a parallel vertical or embedded in each layer — undecided.
  • Economics of log-scale intelligence — a dedicated log agent and behavioral baselining, evaluated before "burning tokens on a million logs a minute."
  • Delegation and decomposition are not specified. Pattern A and Pattern B describe how agents reach resources and each other — not how authority flows when one agent delegates work to a subagent. Authority-subsetting, audience-bound delegated tokens, and audit-chain provenance across a delegation appear in neither this drawing nor the WG1 unified control-plane architecture.
  • Companion drill-downs (persona-creation detail, enforcement-and-audit detail, orchestrator-vs-direct comparison, a combined NOC+SOC shared-enforcement sketch) are referenced but not yet produced.
  • This is a v0.6 working draft prepared for vendor sessions — not a ratified reference architecture.
