Requirements for the Agentic Control Plane

WG1 — One Control Plane, Every Domain· architecture dated 2026-08-06· this spec 2026-09-15· owner: ONUG Collaborative
The architecture map draws four boxes and says this is what every domain runs on. This document says, box by box, what has to be true for that claim to hold — using the working group's own list of 24 requirements as the source of what goes in each box.

Scope and method

This document starts from the diagram, not the list. The "One Control Plane, Every Domain" architecture draws the Agentic Control Plane as four components — Agent Trust Fabric, Registry/Personas/BOM, Runtime Supervision, and Private Open Router — sitting under a Human Oversight & Governance band and above a perimeter of resources agents never touch directly. Each requirement below is placed in the box it belongs to, using the exact wording the WG1 scoping document (Agentic Overlay Alignment Analysis) uses for that item. Every one of the 25 items appears exactly once.

Two labels carry forward from the source analysis: a green bar marks the six items that also map 1:1 to an AOMC control (the externally-validated minimum baseline) — these are non-negotiable regardless of the Fall 2026 track vote. An orange bar marks a requirement the source material itself calls unresolved — an open gap, a field-wide problem, or scope still to be decided.

How to read the plane

Quoted directly from the architecture map's own labels.

Human Oversight & Governance Agent Trust Fabric ★ Registry, Personas & BOM Runtime Supervision Private Open Router ★
  • ★ marks the two components the map calls out as distinctive — Trust Fabric and Private Open Router. Registry/Personas/BOM and Runtime Supervision are just as required; they're simply not the novel part.
  • The plane sits below a governance band and above four governed resources — Enterprise Identity Systems, Telemetry/Sources of Truth, Tools & Enterprise Data, Model Estate — that agents reach only through it, never around it.
  • NOC and SOC (WG2, WG3) are the first two domain personas plugging into this plane. They are not WG1's requirements — they're proof the plane's requirements are domain-agnostic. See "Out of scope" below.

Human Oversight & Governance

"decision rights · approval of personas & task sets · change-stop authority · one oversight model across every domain"

This band sits above the plane, not inside it. Its job is to decide what the plane is allowed to enforce — the plane itself has no authority to set its own risk appetite.

GOV-1item #1
Agentic Control Framework

Publish one classification model for agents (assistant, copilot, workflow agent, autonomous agent, multi-agent system), four risk tiers (low/moderate/high/critical), and a decision-rights matrix that says who approves what at each tier.

Maps to AOMC-6, Governance of Agent Autonomy. This is the document every other requirement's risk tier resolves back to.
GOV-2item #2
Governance Model

Name who owns what: executive sponsor, agent owner, business owner, platform owner, and security — plus the escalation and exception path when they disagree.

GOV-3item #6
Human Oversight Policy

List the decisions that always need a human sign-off (financial commitments, contract changes, customer-impacting actions, production changes) and define the emergency-stop and escalation procedures.

This is where the diagram's "change-stop authority" gets specified.

Agent Trust Fabric ★

"non-human identity · attestation · gateway-held credentials — agents never touch secrets · per-step scoped tokens · least privilege · deprovisioning first · kill-on-drift"

Everything in this box answers one question: how does the plane know which agent this is, and what is it allowed to hold?

TF-1item #5
Agent IAM Standard

Give every agent a unique, non-human identity. Enforce least privilege and just-in-time access. Rotate credentials automatically and manage keys centrally — no agent holds a long-lived secret.

Maps to AOMC-1, Identity, Lifecycle & Attestation.
TF-2item #10
Security Control Baseline (identity half)

Enforce zero trust on every authentication and authorization decision. Prevent privilege escalation. Fail secure by design, and validate the design with red-teaming and penetration testing.

Maps to AOMC-4, Zero Trust Enforcement. The other half of item #10 (resiliency tiers, testing program) lives under Cross-Cutting Assurance below.
TF-3item #16
Multi-Vendor Control Plane

Let agents prove identity, authorization, and accountability across organizational and vendor boundaries — without a shared identity provider or a custom integration per partner.

This is the "federated, no über-controller" property in the diagram's own header. No reference implementation exists yet.
TF-4item #20
Credential-in-Context Protection

Secrets must never enter an agent's prompt, context window, or reasoning trace. Credentials get injected only at the proxy or tool-call boundary, through a secrets manager, with leak detection on everything the agent produces.

This is the literal source of "agents never touch secrets" in the diagram.
TF-5item #21
Agent-to-Next-Hop Authentication

Every hop in an agent's path — a tool server, a peer agent, a direct API call — requires cryptographic proof of identity, so a stolen token is useless to anyone it wasn't issued to.

This is the diagram's "every hop mutually authenticated."

Registry, Personas & BOM

"the persona record: autonomy, model, estate, approved task set · agent bill of materials · data classes · rights & normal-behavior spec (open gap — vendor challenge)"

This box is the record of what each agent is and is allowed to do — the thing every other component checks against.

REG-1item #3
Risk Assessment Standard

One scoring model and template covering financial, security, privacy, compliance, operational, reputational, regulatory, and data-sensitivity risk. This is what sets each agent's risk tier.

REG-2item #4
Inventory and Registry

Track every agent: name, owner, purpose, data it can reach, systems it's connected to, model it runs on, risk classification, approval and production status.

This is the diagram's "persona record."
REG-3item #18
Agent Personas

Identity governance changes with the use case — an ad hoc assistant flow needs different identity handling than a structured, multi-team business process.

REG-4item #23
Agentic Process Notation & Authorization Scope

Extend BPMN 2.0 so each process step carries its objective, authorization-scope reference, data-sensitivity class, volume bound, and a flag for whether it crosses a trust boundary — so the review of what an agent can do lives in the same diagram as what it does.

REG-5item #24
Rights Bill of Materials & Access Reconciliation

Keep a version-controlled inventory of the permissions each process step actually needs, alongside standard AI-BOMs. Reconcile declared access against actual access, classification, and data volume automatically — any mismatch is a finding.

This is the diagram's "rights & normal-behavior spec," explicitly flagged there as an open gap and posed to vendors as a challenge. No product does this today.

Runtime Supervision

"policy check on every message & call · injection filtering (prompt · inferred · hidden-instruction) · composite-authority detection · quarantine · immutable audit journal"

This box watches what agents actually do, in real time, and can stop them.

RS-1item #7
Action Guardrails

Define allowed, restricted, and denied actions with an authorized tool catalog. Enforce rate limits, spending limits, confidence thresholds, and scope boundaries at runtime. Set data-handling, compliance, and regulatory restrictions on what an agent may read, transform, or send.

Maps to both AOMC-3 (Data Guardrails) and AOMC-5 (Secure Orchestration & Tool Authorization) — the source analysis delivers both from this one catalog.
RS-2item #8
Observability and Monitoring

Instrument every agent with telemetry, tracing, action and prompt logging, and decision traceability over immutable data. Run anomaly detection and alert a human in time to abort.

Maps to AOMC-2, Runtime Monitoring & Rogue Agent Detection.
RS-3item #9
Audit and Traceability Architecture

Immutably capture every user request, agent reasoning summary, tool call, action, data access, and approval — enough to support forensics, compliance review, and incident investigation.

This is the diagram's "immutable audit journal," and the evidentiary backbone TF-1's attestation and RS-2's forensic replay both depend on.
RS-4item #13
Incident Response Playbook

Cover runaway agents, unauthorized actions, hallucinated decisions, breaches, data leakage, and policy violations, with defined containment, a kill-switch process, and recovery.

This is the diagram's "quarantine."
RS-5item #19
Inferred Prompt Injection

Defend against indirect injection — content that alters an agent's intent without a direct prompt attack — by filtering what the agent can see, logging both direct and indirect outcomes, and constraining flows to limit blast radius.

This is the "inferred · hidden-instruction" half of the diagram's injection filtering.
RS-6item #22
Aggregate Grant Risk

Evaluate an agent's combined set of grants, not each one in isolation — individually narrow, individually-approved permissions can add up to more authority than intended. Monitor for composite-access patterns, not just single-action anomalies.

Named in the source as a field-wide open problem: no framework today proves a bound on composite authority. Monitoring is the interim compensating control, not a fix.

Private Open Router ★

"every model call routed by cost · risk · sovereignty · certification · right-size the model per task · spend caps · usage attribution — the AI FinOps lever for every domain"

The one component with a single requirement behind it — and the one the source material is most explicit is undefined.

POR-1item #17
Private Open Routing

Route every model call by data sovereignty, tokenomics, AI FinOps cost, and national-security constraints, so cheap models handle routine work and frontier models are reserved for what needs them.

Scope is explicitly undefined in the source: "for the WG to determine and scope the demonstration." Nothing below this line is committed yet.

Cross-cutting assurance not one plane box — the process every box above is enforced through

These four don't correspond to a component on the diagram. They're the wrapper that makes the four boxes above real rather than aspirational.

PROC-1item #11
Agent Lifecycle Management (SDLC)

Eight stages — request, assessment, design, testing, approval, deployment, monitoring, retirement — each with a required artifact (design document, risk assessment, test evidence, approval record).

Every requirement above gets enforced stage by stage through this process, not as a one-time check.
PROC-2item #12
Validation and Assurance Program

Test functionality, accuracy, safety, security, resilience (including chaos testing), performance, and regulatory compliance. Produce test plans, certification reports, and approval criteria.

This is where TF-2's red-teaming and penetration testing actually run.
PROC-3item #14
Compliance and Regulatory Mapping

Map the requirements above to NIST AI RMF, ISO 42001, ISO 27001, SOC 2, the EU AI Act, and applicable industry regulations — proving that meeting this document also satisfies external frameworks.

PROC-4item #15
Operational Metrics and KPIs

Report risk metrics (high-risk agents, violations, incidents), operational metrics (agents in production, override rate, success rate), and business metrics (productivity, cost savings, cycle time).

Has nothing to report on until the requirements above exist in production.

Boundary constraints

The diagram's bottom band isn't a fifth plane component — it's four resources the plane protects by keeping agents out of them directly. Each constraint below is enforced by requirements already listed; this table just states the invariant the diagram draws.

ResourceInvariantEnforced by
Enterprise Identity SystemsAir-gapped from agents. Identity flows out of the plane to the agent, never the reverse — an agent can never reach into an IdP to promote or mint its own authority.TF-1, TF-2
Telemetry, Sources of Truth & RulesetsRead-only to agents. An agent can observe what the estate is and what it should be, but can never rewrite its own baseline or the rules that judge it.RS-2, RS-3
Tools & Enterprise DataReached only through governed MCP gateways the plane authorizes. No direct agent-to-device path exists.RS-1, TF-5
Model EstateHybrid by design (frontier, open-weight, private on-prem). Every model is certified before use, version-pinned, and rolled back on regression.POR-1, PROC-2

Out of scope

  • Domain personas (NOC, SOC, and whatever plugs in next) are not WG1 requirements. WG2 owns the NOC persona, WG3 owns the SOC persona; WG1's obligation ends at making the plane's four components domain-agnostic enough that a new persona can plug in "the same way." Nothing in this document specifies an ops loop, a gate name, or a domain-specific control.
  • The architecture map's date lines don't reconcile: the subtitle reads "Draft v0.2, August 6, 2026" and claims WG1 v0.2 "ratified 7/28," but the alignment analysis has WG1 still mid-scoping in late July. The ratification claim is not corroborated by the sibling source — treat REG-4 and REG-5 in particular as pre-ratification.
  • TF-3, REG-4, REG-5, RS-6, and POR-1 are each marked open above for a different reason (no reference implementation, an explicit vendor challenge, a field-wide unsolved problem, or undefined scope). None of the five should be read as "specified" just because it has a requirement ID.
  • Tier and track assignment from the earlier draft of this document is intentionally dropped here. Priority now follows the diagram's own emphasis (★ components, baseline/AOMC bar, open bar) rather than a separate MUST/SHOULD/MAY scheme layered on top.
